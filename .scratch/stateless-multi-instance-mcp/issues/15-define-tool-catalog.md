# Define the explicit-target tool catalog and per-command declarations

Type: grilling
Status: resolved
Assignee: NateZwainleskPLA
Blocked by: 12, 14

## Question

What is the complete modern tool catalog, and what does each command declare?

Every resolved decision assumes this catalog exists but none defines it. The cutover contract requires one deterministic catalog for every protocol era. The execution-safety contract requires every command to declare Document Access Mode, Cancellation Capability, and Transaction Ownership. The identity contract requires every command to be workstation-scoped, Revit-scoped, or Document-scoped. The out-of-scope rule against broad tool redesign is in tension with all of this, because explicit targets already change every signature.

Produce the catalog: for each existing tool (status, model info, views, current-view elements, levels, families and placement, colours, code execution, document open/close/save/sync, and whatever survives of launch) its scope, its three declarations, whether it is interactive, and any signature change. Add the new control tools: target discovery, health, operation inspection, cancellation, and any status or bootstrap actions. Name each tool and state the Target Runtime command kind it maps to. Record which tools are dropped and why.

[Decide the fate of the Revit launch and installation-discovery tools](12-decide-launch-tools-fate.md) retains both workstation tools in every transport and protocol era. Specify their adapter-local handling where no Target Runtime command applies, the explicit helper bootstrap invocation and host-seed handoff, the disabled-launch error, and launch results that distinguish process creation, extension readiness, and exposed-target discovery without revealing disabled-host metadata. Define a bounded readiness observation and what ends the pending-launch lifetime extension, correlation with the newly launched process rather than any responding Routes endpoint, and retry behavior that does not imply target-owned operation deduplication before a target exists. Preserve the resolved launch-permission and adapter-lifetime rules.

## Answer

### Common request contract

- Retain all 20 existing named tools. Add `discover_revit_targets`, `get_revit_operation`, and `cancel_revit_operation`, for 23 tools total. Every supported protocol era and transport gets the same deterministic schemas. Unsupported runtime capabilities produce explicit tool errors rather than changing the catalog.
- In the table, `R` means required `revit_target`; `D` means required `document_target`; `S` means required caller-generated `submission_id`. Every queued command requires `R, S`; Document-scoped commands also require `D`. Target and submission validation, fingerprints, retention, five-second inline handoff, and error semantics remain owned by their existing decisions.
- `ctx` is SDK-injected context, not a caller argument. Retain the existing business arguments unless a change is stated below. Names for new arguments and command kinds below are the catalog contract. R, D, S, view_id, and operation are string fields; flags are booleans. Existing business-argument types remain as declared by the current tool functions unless changed here. Apply schema defaults before fingerprinting, so an omitted default and its explicit value represent the same command.
- Document Access Mode is `database` or `ui` for document operations, and not applicable when no document is addressed. Database mode permits both reads and writes. A fixed built-in declaration cannot be overridden by a caller to bypass its execution requirements.
- Add `allow_ui_change: bool = false` to commands that can activate or close a visible document, change the active view, or otherwise deliberately change the user's UI. It is an explicit request by the agent, not a request for another human confirmation. If the requested operation needs such a change without this flag, return `ui_change_required` before that change; never silently upgrade database access to UI access. Include this flag in the immutable submission fingerprint.
- Add `interactive: bool = false` only where the table permits Local User Interaction. It allows supported prompts or picking; it is distinct from merely changing the visible document. A request for Local User Interaction also requires `allow_ui_change=true`. Missing up-front choices fail before admission where possible, or complete with an error if discovered during execution. No operation waits for another MCP round trip to obtain input.
- UI changes caused by explicitly requested document open/close and launch are disclosed in the tool description and result. Closing a visible document may make another document active; there is no promise to restore the prior visible document. Model changes may visibly refresh an already displayed view without switching documents; `allow_ui_change` controls UI actions, not suppression of normal Revit redraw.
- Arbitrary code remains privileged. The declarations govern the context injected by the runner and the behavior the code promises; they do not intercept every Revit API call or sandbox UI actions.
- All commands are cancellable while queued. `queued_only` makes no promise of interrupting a running Revit API call. `cooperative` requires documented checkpoints; it never means thread abortion. For arbitrary code, checkpoints are calls to the supplied `cancellation_requested()` helper.
- Transaction Ownership describes transactions owned by the command runner, not every possible side effect. In particular, `none` on save, sync, open, close, image export, or launch does not mean side-effect-free. Results must separately describe known persistence, filesystem, and UI effects; never claim a failed save or sync was rolled back merely because no runner-owned transaction exists.

### Views and colors

- View IDs are document-local element identifiers, serialized as decimal strings and validated within the addressed live Document Target. They are not new workstation-wide handles. Results from view listing and current-view inspection include the exact ID needed by export and coloring. Unknown, deleted, wrong-kind, or unsupported views fail explicitly; there is no fallback by name or active view.
- The current-view tools read the addressed document's actual active UI view at execution and echo its ID. If that document is inactive, `allow_ui_change=false` produces `ui_change_required`; `true` permits activation followed by revalidation. They do not silently return information from another document. A current-view query is observational and does not pin a later command; later view-specific work uses the returned explicit ID.
- Exporting an addressed view must not activate it as a fallback. An export path needing activation is unsupported under this database-mode command unless a later decision explicitly adds an opt-in mode.
- Coloring and clearing affect exactly the addressed view by default. The user explicitly requested retaining the existing propagation loop as a tool flag: `apply_to_same_view_type=true` additionally applies the operation to every other non-template view in the addressed document with the same Revit `ViewType` as the addressed view. This is an explicit broad-view request and requires no activation of those views. The flag is part of the immutable submission fingerprint.
- Existing code already applies an override to one view and separately loops over matching ViewTypes, so gating that loop is the expected narrow change. No extensive workaround is authorized by the user's conditional acceptance. If a view cannot support the operation directly, report that limitation; never broaden the scope when the flag is false. Resolve and validate the affected view set at execution before mutation, return its IDs, and keep the entire requested batch within the command's atomic transaction.
- Preserve the current whole-document category selection for coloring, but apply resulting per-element overrides only in the explicitly requested view set. The command does not promise to color only currently visible elements. Validate parameters and color input before mutation; report counts of selected, changed, and skipped elements with reasons, including the affected views.
- Preserve the existing reset-all-element-overrides implementation within the requested view set and require explicit `reset_all_overrides=true`. The tool description must disclose that this removes unrelated element-level overrides too. `false` returns `unsupported_clear_mode` with no effects. Do not promise restoration of an earlier appearance or introduce a persistent override-history store.
- Color batches check cancellation before starting, between elements, and before commit, inside one runner-owned transaction. Error or acknowledged cancellation before commit rolls back all changes. A commit that wins completes normally.

### Code and document behavior

- Document-scoped code receives `doc` bound to D. In database mode, injected `uidoc` is `None` even when that document happens to be active; the runner does not activate it. In UI mode, the runner binds `uidoc` only to D after checking whether an explicitly permitted activation is needed. The agent remains responsible for deliberate direct API/UI access through unrestricted code.
- Revit-scoped code deliberately omits D and may manage multiple documents or use the active context. The `document_access` default has no document-selection meaning in this scope; reject a nondefault value rather than pretending there is a document to bind. Supply application context and active `doc` when available; supply active `uidoc` only with explicit UI permission. `allow_ui_change=false` remains the code's declaration that it will not deliberately change UI, rather than an enforced sandbox.
- A request to open and activate a document explicitly needs `allow_ui_change=true`. Return its eligible Document Target only after successful registration, or an explicit registration/identity failure with known open effects. Never equate a successful API call with an unverified local-copy creation. Preserve detach/audit choices and report what was actually opened.
- A close request must supply `save=true` or `save=false`. `false` explicitly requests discard; it is not an omitted default. If `true`, a save failure stops the close. Do not post an asynchronous Close command and report immediate success. Completion requires verifying that the addressed document closed. If an API/UI limitation prevents the requested behavior, return an explicit unsupported/error outcome; do not activate it without permission or claim completion from merely posting a command.
- Save As requires `overwrite=true` before replacing an existing file and `as_central=true` before intentionally creating a central model. An ordinary save uses the existing document identity; Save As changes metadata, not D. Reject `overwrite`/`as_central` options that have no meaningful application to the supplied request. File persistence success and model effects must be reported honestly even when later reporting fails.
- Sync requires an addressed workshared document and preserves the existing comment, compact, and relinquish choices. Do not add a runner transaction around native save/sync calls. Unexpected prompts are not an implicit input channel; supported dialog cases follow the declared interaction mode, while unhandled cases follow containment/quarantine rules rather than promising a universal modal-dialog suppressor.
- `place_family` uses one atomic transaction for all requested placement, rotation, and property changes. Invalid or unsupported requested changes fail rather than silently committing partial placement. Preserve the current handler's conventions: x/y/z and double-valued properties are passed in Revit internal units without conversion; rotation is supplied in degrees and converted to radians. Publish these units in the tool description. Do not add an unrelated units-conversion redesign to this migration.
- The host runtime prototype must verify the feasibility of these UI, close-completion, and cooperative-checkpoint contracts. This catalog does not claim those runtime mechanisms already exist or promise interruption of native save/open/sync calls.

### Control tools and status

- `get_revit_status()` reports adapter identity/version/interface compatibility and safe aggregate host/exposure counts. Zero documents or zero exposed targets is a usable adapter state, not automatically an unhealthy endpoint. With R supplied, it additionally returns addressed target health and queue/quarantine state without entering the execution queue; it does not activate or inspect live documents through an API-context handler.
- `discover_revit_targets()` returns the single nested Target Snapshot already specified, including eligible document metadata only for exposed hosts. It remains the sole full discovery tool. Disabled hosts contribute only permitted aggregate counts.
- Status, discovery, inspection, and cancellation do not require S and do not create Revit Operations. Queue bypass does not permit unsafe off-thread Revit API reads: control-plane freshness and host scheduling remain subject to the runtime prototype and existing acceptance bounds.
- Local-only actions remain on the Revit MCP Status surface or local configuration: enabling exposure, changing future-host defaults, granting launch permission, changing endpoint/configuration, resetting quarantine, and evidence cleanup/export. No MCP configuration or repair tools are added.

### Bootstrap and launch

- Bundled entry-point contract: `RevitMCPAdapter.exe start --transport http` starts or reuses the canonical endpoint and exits with machine-readable readiness or an explicit startup error; `RevitMCPAdapter.exe serve --transport stdio` serves its invoking client. Use `RevitMCPAdapter.exe` as the bundled executable filename; signing identity and release ownership remain with their existing decision ticket. The HTTP start command launches its serving child without a visible console window, then exits after verification; stdio keeps protocol stdout free of startup diagnostics.
- A host may supply `--host-seed <registration-path>` to HTTP startup. The argument is an absolute path to the launching host's native pyRevit registration file, passed as one argument. It is advisory, not a target ID or selected-session state. It is not a path for executable code or a product-owned storage root. Validate owner, process lifetime, and interface compatibility before use; a seed never grants exposure or replaces normal workstation discovery. An invalid seed is reported without routing through it. All hosts and client startup share the existing mutex, descriptor, identity checks, and explicit port-collision behavior.
- HTTP startup returns readiness only after the endpoint identity/compatibility check succeeds. It does not itself launch Revit. Normal host-cooperative lifetime, the five-minute default zero-host startup window, and client-lived stdio remain as previously resolved.
- Installation discovery remains available independently of launch permission. Launch checks the persisted default-off setting and returns `launch_disabled`, `process_created=false` if disallowed. MCP input cannot enable that setting. A launch requires `allow_ui_change=true` in addition to the persisted launch permission; a file-associated startup that may need supported local dialogs must declare `interactive=true` or be rejected before process creation if it cannot honor unattended execution.
- Retain `timeout` as a readiness-observation bound, default 120 seconds, valid range 0–600 seconds; 0 requests creation-only observation. It never kills Revit or claims launch failure merely because readiness was not observed. Launch is adapter-local workstation work, not a Revit Operation, and is outside the target-command five-second inline handoff rule.
- Keep the newly created process handle internally and correlate PID plus process creation identity with the extension's registration. Never accept any responding Routes endpoint as evidence about this launch. Do not expose metadata from an unexposed host: safe launch receipt fields describe the adapter's own process-creation attempt, while extension readiness is an opaque correlated boolean and target metadata appears only through permitted exposed-target discovery.
- Launch result fields: `process_created`, `launch_outcome` (`not_started`, `observed`, or `observation_incomplete`), `extension_ready` (boolean or unknown), `exposed_revit_target` (nullable), `observation_end_reason` (`not_started`, `creation_only`, `host_registered`, `process_exited`, `deadline`, or `adapter_failure`), elapsed observation duration, and structured error where applicable. `exposed_revit_target=null` alone never distinguishes a disabled host from one not yet exposed/observed. A supplied file path is recorded as requested input, never as a verified opened document. A compact explicit target discovery can follow an exposure transition.
- End the pending-launch lifetime extension when the correlated host registers (normal host lifetime takes over), the created process exits, or the observation deadline is reached. Client disconnection does not restart the launch or extend that deadline; observation can continue only to its fixed bound. Adapter failure loses the observation; it does not terminate the created Revit process or retain authoritative operation state.
- Never automatically retry a process-creation call or ambiguous launch delivery. A lost reply leaves the outcome unknown; use exposed-target discovery and, when necessary, the person's local inspection before deliberately requesting another process. Do not invent target-owned S/op guarantees before a target exists, or use the Forensic Record to replay a launch.

### Resolution and follow-through

- The user accepted explicit agent control of UI changes, up-front document-operation choices with opt-in local interaction, bounded process-correlated launch observation, single-view coloring by default with the existing same-ViewType loop retained as a flag, and explicit reset-all clearing. The remaining catalog declarations apply those choices and the already-resolved target, operation, and safety contracts. No migration implementation is part of this resolution.
- No existing named tool is dropped. Implicit target selection, propagation without the flag, unacknowledged reset-all clearing, and success claims based only on posting a UI close command are removed behaviors. Status becomes control-plane health; model details remain with model info and Target Snapshot discovery.
- [Prototype the in-Revit execution lane and control plane over pyRevit Routes](17-prototype-host-execution-lane.md) must verify explicit-UI behavior, close completion, atomic cancellation checkpoints, and control-plane access under the chosen engine. Failure to meet these contracts requires an explicit amendment or declared unsupported case, never an implicit UI fallback or extensive color workaround.
- [Define the migration sequence and rollback checkpoints](11-define-migration-sequence.md) selects release/checkpoint coverage from this catalog and the existing acceptance contract. The full catalog is deterministic within each shipped package and never changes according to the negotiated protocol era, transport, exposure, or launch setting.
- Validation of this planning artifact checks current-tool coverage, declaration completeness, relative links, resolved-state bookkeeping, and agreement with existing scope/lifecycle decisions. Live Revit feasibility remains the prototype and implementation acceptance work.
