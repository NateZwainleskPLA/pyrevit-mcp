# Choose MCP adapter topology and durable state ownership

Type: grilling
Status: resolved
Blocked by: 01, 02

## Question

Where should the MCP interface, Revit instance discovery, per-target execution coordination, and durable Revit Operation state live so the MCP-facing layer can remain disposable, the product retains one pyRevit-extension footprint, and a future broker or remote adapter could be introduced without changing every tool interface?

## Answer

Use one disposable MCP Adapter per active Windows user as the canonical modern endpoint. It is an on-demand helper bundled inside the pyRevit extension and exposes MCP `2026-07-28` Streamable HTTP at one stable, configurable loopback URL. It owns the MCP interface, request validation, catalog presentation, Target Snapshot assembly, and routing, but no authoritative Revit Runtime State or Revit Operations. Stdio is an optional development or compatibility adapter, not the target topology.

The first live Revit Host starts or reuses the adapter under a per-user launch mutex. Every host cooperatively health-checks it and may restart it after acquiring that mutex; the helper is not owned by the particular Revit process that launched it. It runs while Revit Hosts exist even when none is exposed as a Revit Target, allowing an agent to learn that targets require user exposure. In normal host-cooperative operation, it exits after pyRevit discovery reports no live Revit Hosts for a configurable grace period. Explicit client startup may also bring up this same adapter before any Revit Host exists, supporting installation discovery and permission-gated cold launch under the startup-window and lifetime rules in [Decide the fate of the Revit launch and installation-discovery tools](12-decide-launch-tools-fate.md). An occupied configured port is accepted only after a compatibility health check proves the listener is this adapter, otherwise startup reports an explicit collision rather than silently moving the endpoint.

Discover local Revit Hosts and their execution endpoints through pyRevit's native Routes server registry. A starting host supplies its Routes endpoint as a bootstrap seed whether it starts or reuses the adapter; the adapter asks it for sister endpoints, then queries this extension on every reachable sister. A client-started adapter with zero hosts has no host seed until one becomes available. An enabled exposure returns and validates the opaque Revit Target and its metadata; a disabled host contributes only to the privacy-preserving availability count defined by the installation contract. Native Routes records, process IDs, and ports are discovery hints rather than Revit Target identity. Ignore stale and unrelated registrations, and revalidate the addressed opaque target on every routed request. Do not add a second host-registration directory, port-range probing, DNS-SD advertisement, or other client-side host-discovery mechanism.

Each Revit Target is the sole authority for its Document Targets, serialized execution coordination, and Revit Operation registry. Keep authoritative operation records in that Revit process's memory, with optional target-owned temporary files for large results. A Revit Operation survives MCP requests, client disconnections, and MCP Adapter restarts while its owning Revit Target remains live; it expires irrecoverably with that target and is never adopted by a new target generation. No database or recovery journal reconstructs it.

Place a small command-oriented Target Runtime interface between MCP tools and execution targets. It covers target description and validation, explicitly targeted command submission, and Revit Operation inspection or control; the operation-lifecycle decision owns the exact methods and schemas. The local pyRevit Routes adapter implements this interface now. A future broker or remote adapter can implement the same interface without changing MCP tool contracts. Any migration reuse of existing tool-specific Routes is governed by [Retire the temporary legacy execution path from the target-identity decision](14-retire-legacy-execution-path.md); it is not a separate legacy protocol or execution adapter.

Diagnostics are durable but non-authoritative. The MCP Adapter and each Revit Target write separate, correlated streams beneath the fixed product root defined by [Reconcile the per-user storage root across topology, installation, and Forensic Record decisions](13-reconcile-storage-root.md). That ticket owns the shared Local AppData resolution contract for the Connection Descriptor, product settings, and evidence. The Forensic Record includes exact submitted automation code as separately identifiable forensic artifacts, but it never resumes, replays, or decides the state of an operation. [Define the Forensic Record contract](10-define-diagnostic-journal.md) owns its event schema, permissions, retention, redaction of non-code data, rotation, export, and cleanup.

Concurrent interactive sessions belonging to different Windows users do not share one adapter. If they need simultaneous endpoints, their per-user configuration must select non-conflicting ports; automatic cross-user endpoint allocation is outside this topology.
